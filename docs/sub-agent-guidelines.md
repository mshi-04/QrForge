# QrForge サブエージェント運用ガイドライン

## 基本方針

- サブエージェントは作業の丸投げ先ではなく、Rust core・JNI bridge・Kotlin wrapper・sample app の視点を分けるために使う。
- 親エージェントは、対象範囲、責務境界、最終判断、差分統合に責任を持つ。
- 実装担当の視点だけで完結させず、必要に応じて別視点で設計・レビュー・検証を見る。
- サブエージェントの結果は、親エージェントが `docs/architecture.md`、`docs/review-rules.md` と照合してから採用する。
- 軽微な修正では無理に使わない。

## 使う場面

- Rust core、JNI bridge、Kotlin public API、sample app の複数レイヤーにまたがる変更
- 対象範囲、やらないこと、完了条件の整理
- Rust core に Android/JNI/Kotlin 依存が混ざっていないかの確認
- JNI bridge が型変換とエラー変換に留まり、QR 生成ロジックを持っていないかの確認
- `QrForge`、`QrOptions`、`QrForgeException` など public API の互換性確認
- 実装後レビュー、テスト不足の洗い出し、CI 失敗調査
- PR 前の変更概要、確認コマンド、残るリスクの整理

## 使わない場面

- typo 修正
- コメントや文言だけの小さな修正
- 1 ファイル内で完結する軽微な変更
- 親エージェントだけで責務境界と確認結果を判断できる場合
- 使うことで作業や報告が過剰になる場合

## 推奨役割

- 調査担当: 既存 docs、対象ファイル、影響範囲を確認する。
- 実装担当: 指定された対象範囲とレイヤ範囲だけを変更する。
- レビュー担当: `Critical`、`Suggestion`、`Nitpick` の観点で差分を見る。
- テスト確認担当: 変更箇所に応じて Rust、JNI、Kotlin、sample app の確認コマンドを整理する。
- 要約担当: PR 前に変更内容、確認結果、未確認事項を短くまとめる。

## 分担ルール

- 依頼時に、対象レイヤ、変更してよいファイル、触らない範囲を明示する。
- Rust core と JNI bridge、Kotlin wrapper と sample app の責務を混ぜない。
- 同じファイルを複数担当で同時に編集させない。
- 調査、実装、レビュー、検証は視点を分けるが、最終統合は親エージェントが行う。
- サブエージェントの指摘はそのまま採用せず、根拠となるコード、差分、テスト結果、docs を確認する。
- 実行していない確認コマンドを「通った」と書かない。

## PR 前チェック

- 依頼範囲の「やらないこと」を越えていないか確認する。
- Android app が `QrForge` wrapper 経由で利用しているか確認する。
- JNI native binding が public API として露出していないか確認する。
- `.so` を再生成した場合は、意図した成果物か確認する。
- docs のみの変更では、コード変更が混ざっていないことを Git 差分で確認する。
- 最終報告には、変更ファイル、確認コマンド、未実施項目を含める。
