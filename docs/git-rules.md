# QrForge Git 運用ルール

## 目的

この文書は、QrForge で Git 操作を行うときの共通ルールを定義する。
コミット、ブランチ、レビュー対応の表記を揃え、変更履歴を日本語で読みやすく残すことを目的とする。

## コミットメッセージ

- コミットメッセージは日本語で書く。
- 1 行目は変更内容が分かる短い要約にする。
- 何を変更したかが伝わる動詞を含める。
- 英語の Conventional Commits 形式は必須にしない。
- ライブラリ名、API 名、コマンド名、ファイル名は原文のまま書いてよい。

良い例:

```text
Rust core の QR PNG 生成を追加
```

```text
JNI bridge のエラー変換を整理
```

```text
Kotlin wrapper の公開 API を調整
```

避ける例:

```text
Add Rust QR core crate
```

```text
fix
```

```text
update files
```

## 複数行コミットメッセージ

必要な場合は、1 行目に要約を書き、空行を挟んで詳細を書く。
詳細には変更理由、責務境界、確認したコマンドを簡潔に書く。

```text
Rust core の QR PNG 生成を追加

文字列から PNG byte array を生成する最小 API を追加。
JNI bridge と Kotlin wrapper にはまだ責務を広げない。
```

## コミット前確認

- `git status --short --branch` で対象外の変更を巻き込まないことを確認する。
- 既存の未コミット変更がある場合は、依頼範囲と無関係な変更を勝手に戻さない。
- 実装変更を含む場合は、関連する確認コマンドを実行して結果を報告する。
- 確認コマンドが環境要因で失敗した場合は、失敗理由をコミット後の報告に含める。

## ブランチ命名規則

- `feature/<topic>` 形式を使う。topic は実装内容が分かる短い英語にする。
- 例: `feature/rust-core`、`feature/jni-bridge`、`feature/kotlin-wrapper`
- ブランチは `main`（またはデフォルトブランチ）から作成する。
- 現在のブランチが使える場合は新規作成せず、完了後に PR で `main` へ取り込む。

## PR 説明のガイドライン

- タイトルは日本語で変更内容を短く表す（例: `JNI bridge の最小実装を追加`）。
- 本文には「何を変えたか」「なぜ変えたか」「確認コマンドと結果」を簡潔に書く。
- Phase の完了条件を満たしていることを確認してから PR を作成する。

## AI エージェント向けルール

- ユーザーから明示された場合を除き、英語コミットメッセージでコミットしない。
- コミットメッセージを自動生成するときも、日本語の要約を優先する。
- 依頼範囲外の変更が作業ツリーにある場合、その変更を混ぜずにコミットする。
- コミット後はコミット hash、メッセージ、確認結果を報告する。
