## 手順

1. 依頼から影響を受けるレイヤーを特定する
2. 対象レイヤーに必要な docs だけを読む（下記「読む docs」参照）
3. 対象範囲・責務境界・変更予定ファイル・実行する確認コマンド・やらないことを提示する
4. 実装する
5. `rust/` を変更したなら `.so` 再ビルドの要否を判断する（下記「判断すること」参照）
6. 変更レイヤーに対応する確認コマンドを実行する
7. 報告する（下記「報告」参照）

## 読む docs

skill には規則を書かない。判断が必要になった時点で該当の docs を読む。

| 迷っていること | 読む docs |
|---------------|-----------|
| どのレイヤーの仕事か、依存方向は正しいか | `docs/architecture.md` |
| 実装ルール、禁止事項、命名 | `docs/coding-rules.md` |
| public API、例外の分類、`QrOptions` 定数 | `docs/api-design.md` |
| テストを足す・直す | `docs/unit-test.md`（詳しくは `unit-test` skill） |
| 確認コマンド、`.so` 再ビルド、cargo の注意 | `docs/setup.md` |

## 判断すること

この skill が担保するのは規則の暗記ではなく、以下を**明示的に判断すること**。

- **レイヤーを広げない**。原則は 1 レイヤーに閉じ、依頼や public contract の同期が複数レイヤーを
  必要とする場合だけ対象を増やす。境界をまたぐ場合は、実装を進める前に各レイヤーの変更理由を提示する。
- **`.so` の鮮度**。`rust/` を変更したら `qrforge/src/main/jniLibs/<abi>/libqrforge.so` は
  古いままになる。Android 側の確認を行うなら再ビルドが必須で、行わないなら「native 側は未検証」
  と明記する。どちらなのかを曖昧にしない。手順は `docs/setup.md`。
- **確認コマンドの選択**。`docs/setup.md` の「変更後の確認フロー」から、変更レイヤーに対応する
  ものを選ぶ。実行できないものがあれば理由とともに未実施として扱う。
- **依頼範囲外の変更を混ぜない**。作業中に見つけた別の問題は、直さずに報告する。

## 報告

1. 変更ファイルと、それぞれどのレイヤーか
2. 実行した確認コマンドと結果
3. 実行しなかった確認と、その理由（環境要因を含む）
4. 残るリスク・未検証の振る舞い

実行していない確認を「通った」と書かない。
